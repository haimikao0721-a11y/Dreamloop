## 一、为什么改，代价是什么

**改的原因**：格子回合制的操作感是"点一下走一步"，玩家要的是"推着走"。

**代价要说清楚**，因为这次要废掉的东西里有四轮平衡试错换来的成果：

| 作废 | 保留 |
|---|---|
| `combat.ts` 全部 | 叙事层（槽位 / 节点 / 选项 / flag / 结局） |
| `engine.ts` 的回合部分 | 内容数据（角色 / 物品 / 剧情 / 结局） |
| 地图的格子移动 | 条件与效果词汇表 |
| 撞上去就打的战斗 | 死亡即叙事、幕级存档 |
| 前面调的平衡数值 | `assets/` 素材管线 |
| 约一半测试 | 三个模式的架构 |

**一句话**：死掉的是"怎么打"，活着的是"打完之后发生什么"。
而后者才是这个项目的卖点。

**实现差异**：四步做完了，但这张表里"作废"的东西**一个都没删** ——
`combat.ts`、`engine.ts`、格子移动、撞上去就打的战斗、前面调的平衡数值、
`engine.test.ts` / `content.test.ts` 全都还在跑，而且默认入口走的还是它们。
实时层目前是一条**并行的路**（`?proto=rt`），不是替换（见第十五节第 4 步）。

## 二、核心循环：`tick` 与 `reduce` 并存

这是整篇最重要的一个决定。

```
tick(state, input, dt)  → { state, events }     // 一秒 60 次，连续模拟
reduce(state, intent)   → { state, events }     // 玩家按下的那一下，离散命令
```

**为什么不把 `reduce` 也吃掉**：因为"选哪个选项""用哪件道具""下不下楼"这些
**本来就不是连续量**。硬塞进 `tick` 会让每一帧都在判断"玩家是不是又按了一次选择"，
是把简单问题复杂化。

分工：

| 走哪条 | 管什么 | 例子 |
|---|---|---|
| `tick` | **时间在流动的东西** | 移动、敌人 AI、攻击帧推进、理智流失、蜡烛燃烧、刷怪 |
| `reduce` | **玩家按下的那一下** | 选择选项、使用道具、下楼、交互、开关菜单 |

```
phase: 'playing'  →  tick 推进，reduce 收全部离散命令
phase: 'story'    →  tick 冻结，reduce 只收 choose
phase: 'dead'     →  tick 冻结，reduce 只收 restartAct
```

`phase !== 'playing'` 时**模拟整个冻结** —— 这正是"停住操作是规则"那条
（见 `05-表现与文字.md`）。

**顺带解决一个隐患**：剧情期间不模拟，所以"玩家读了多久"不影响任何数值。
"动画时长拖进种子复现"这个问题被结构性地排除了，不需要额外约定。

**实现差异**：实时层**没有 `reduce`**。`tick` 的真实签名是
`tickRt(state, input) -> GameEvent[]`，`DT` 是 `loop.ts` 里的模块常量，不随调用传进来。
选择项、拾取、插蜡烛都是普通函数（`chooseInStory` / `tryPickup` / `plantCarriedCandle`），
原型里由 DOM 回调直接调用，**不经过任何命令通道** —— 代价见第十六节第 1、4 条。

## 三、固定时间步：确定性的地基

```ts
const TICK_RATE = 60;         // 每秒 60 次模拟
const DT = 1 / TICK_RATE;     // 每次固定 1/60 秒，永远是同一个值
```

**渲染帧率不等于模拟帧率。** 外面累加真实时间，够一个 `DT` 就跑一次 `tick`：

```
累加器 += 这一帧真实经过的时间
while (累加器 >= DT) { tick(state, input, DT); 累加器 -= DT; }
渲染(state)        // 可能一帧跑 0 次、1 次或 2 次 tick
```

**为什么必须固定步长**：浮点运算不满足结合律，`(a+b)+c !== a+(b+c)`。
如果 `dt` 随帧率浮动，同一个 seed 在 60Hz 手机和 120Hz 手机上会走出**不同的结果** ——
神种分享、bug 复现、回放录像全部失效。

固定 `DT` 之后：**同一份 seed + 同一条输入时间轴 = 完全相同的一局。**
这是本项目从回合制继承下来的最重要的一条资产，不能丢。

| 项 | 值 |
|---|---|
| 模拟频率 | 60 Hz，固定 |
| 单次上限 | 一帧最多补 5 次 tick（防止卡顿后"追帧"雪崩） |
| 用整数存的量 | 一切帧数、计时器（单位：tick） |
| 用浮点存的量 | 只有坐标、速度、朝向 |

**实现差异**：最后两行只对了一半。`san` 是浮点（`rate * DT`、`drain * DT` 直接累加），
`LightSource.rate` 和 `sanDrain` 的单位也是"每秒"。
代码里守的规矩是**帧数、计时器、燃料走 tick 整数，速率走每秒浮点** ——
`types.ts` 的 `LightSource` 注释写明了为什么分开：速率给策划看（+2/秒），
燃料给模拟用（精确到帧）。

## 四、坐标与碰撞

**单位用像素**（不是格）。一格 = 16 px。

```ts
interface Vec2 { x: number; y: number }

interface Body {
  x: number; y: number;      // 中心点，浮点
  hw: number; hh: number;    // 半宽半高（AABB）
  vx: number; vy: number;    // 速度，像素/秒
}
```

**为什么用中心点 + 半宽半高**：翻墙、卡角、贴边这些 bug 全都出在
"矩形四条边怎么和别的矩形比"。用中心点表示，判定就一行：

```ts
const hit = Math.abs(a.x - b.x) < a.hw + b.hw
         && Math.abs(a.y - b.y) < a.hh + b.hh;
```

### 碰撞分层

| 层 | 挡谁 | 说明 |
|---|---|---|
| **墙** | 所有人 | 地形，实时层是 `TILE_WALL = 1`（回合制那边叫 `TileKind: 'wall'`） |
| **门** | 所有人 | 房间没清完时是关的，清完自动开 |
| **实体** | 不挡 | 玩家和怪物**互相穿过**，只有攻击判定 |

**实体不互相碰撞**是刻意的：实时动作游戏里怪物互相挤会把玩家卡死，
而且"被一坨怪堵在墙角"是纯粹的挫败，不产生任何决策。
Isaac / 元气骑士都是这么做的。

**实现差异**：**门没做**。地形只有 `TILE_FLOOR = 0` / `TILE_WALL = 1` 两种，
`TileMap` 里没有门、没有房间编号，"没清完时是关的、清完自动开"没有对应代码
（`assets/map/door.png` 生成了，没人加载）。

另外两条计划里没写、写代码时定下的：越界一律当墙（`isSolid`），
所以实体永远出不了地图；位移是**分轴**做的（先走 X，撞了修 X；再走 Y，同理），
撞上时**吸附到格子边缘**而不是退回移动前的坐标 ——
退回去会永远停在离墙 1~2 px 的地方，看起来像浮空，贴墙走还会肉眼可见地抖。

### 移动

```ts
// 输入向量已经归一化，长度 ≤ 1（摇杆可以推一半 = 走一半）
body.x += input.moveX * speed * DT;
body.y += input.moveY * speed * DT;
```

**斜向不加速**：输入向量先归一化。不做的话斜着走快 41%，玩家会一直斜着走。

## 五、输入：摇杆向量

`Intent` 里那个 `move` 带方向枚举的写法作废。新的是**连续向量**：

```ts
interface InputState {
  moveX: number;    // -1 ~ 1
  moveY: number;    // -1 ~ 1
  attack: boolean;  // 边沿触发：只在按下的那一 tick 为 true
  use: boolean;     // 拾取 / 交互
}
```

四种输入源都产出同一个 `InputState`：

| 设备 | moveX/moveY 怎么来 | 力度 |
|---|---|---|
| **手机轮盘** | 触点相对轮盘中心的偏移 | **有**（推一半走一半） |
| 键盘 | WASD / 方向键，归一化 | 无（只有 0 或 1） |
| 手柄 | 左摇杆原始值 | **有** |
| 鼠标 | 按住时朝指针方向 | 无 |

**轮盘用力度、键盘不用**是必然的：键盘没有模拟量。
所以**任何玩法都不能依赖"力度"**（比如"轻推是潜行"），否则键盘玩家玩不了。

**实现差异**：实际接上的只有**轮盘和键盘**两种（`ui-web/rt-view.ts`），手柄和鼠标没接。
`core/rt/input.ts` 提供了 `clampMove` / `keysToVector` / `wheelToVector`，
但原型**在 UI 里又各写了一遍归一化**（`refreshKeys` / `wheelMove`），
core 那三个函数目前只有测试在调 —— 一条规则两份实现，迟早对不上。
`use` 字段存在，但**从来没有被赋过 `true`**：交互键 E 是在 DOM 回调里
直接调 `tryPickup(state, [])`，绕开了 `tick` 和 `InputState`。

**`attack` 必须边沿触发**。按住不放每帧都是 `true` 的话，
攻击会在收招结束的瞬间自动接下一次 —— 变成"按住就自动打"，
起手帧的意义就没了。

## 六、帧数据：动作定义

全部以 **tick** 为单位（60 tick = 1 秒）。

```ts
interface ActionDef {
  id: string;
  startup: number;     // 起手帧：按下 → 判定出现
  active: number;      // 判定帧：能打到人的窗口
  recovery: number;    // 收招帧：判定结束 → 能动
  // 判定形状（见第七节）
  range: number;       // 攻击距离，像素
  arc: number;         // 扇形角度（度）。360 = 全方位
  damage: number;
  knockback: number;   // 击退距离，像素
  moveX: number;       // 出招时的位移（冲刺攻击用），像素
  moveY: number;
}
```

三段帧的含义**不是数值，是给玩家的信息**：

| 阶段 | 玩家看到什么 | 设计意图 |
|---|---|---|
| **起手** | 武器抬起来 | **这是"能躲"的窗口。** 没有起手 = 玩家只能靠反应，不是靠读 |
| **判定** | 武器扫过去 | 只有这一段能打到人 |
| **收招** | 武器垂下去 | **这是"打空要付代价"的窗口。** 没有收招 = 无脑连按最优 |

**起手和收招是这套系统存在的全部理由。** 只有判定帧的话，
这游戏就退化成"谁按得快谁赢"。

### 初值（与 `src/data/rt/actions.ts` 一致，尚未按试玩调整）

| 动作 | 起手 | 判定 | 收招 | 合计 | 范围 | 伤害 |
|---|---|---|---|---|---|---|
| 记梦者 · 轻击 | 6 | 3 | 9 | 18 (0.30s) | 20 | 3 |
| 记梦者 · 重击 | 14 | 5 | 20 | 39 (0.65s) | 28 | 7 |
| 值夜护士 · 轻击 | 8 | 4 | 11 | 23 (0.38s) | 18 | 4 |
| 值夜护士 · 重击 | 18 | 6 | 24 | 48 (0.80s) | 24 | 9 |

**两个角色的差别不在伤害，在帧数**：

- **记梦者**：起手快、范围大、**伤害低**。靠"打一下就撤"活着。
  和它"瘦、脆、理智高"的定位一致。
- **值夜护士**：起手慢、范围小、**伤害高、收招长**。每一次出手都是赌博。
  和它"稳、能扛、理智低"的定位一致。

**为什么轻击重击要差这么多帧**：如果轻击全面优于重击，重击就是废字段。
差距必须大到"面对快速怪只能轻击、面对大怪必须重击"。

**实现差异**（数据表和上面这套说明之外，还有四件事要说清楚）：

| 项 | 做成了什么样 | 后果 |
|---|---|---|
| 出招期间能不能动 | **完全不动**：`loop.ts` 第 ② 步把不能出招的实体的 `vx/vy` 直接清零 | 抬手才"读得出来"；也意味着没有"边走边打" |
| `moveX` / `moveY`（冲刺位移） | 机制实现了（`actionDash`，只在起手帧生效），但**六个动作的数据全是 0** | 冲刺目前没有任何一招在用 |
| `knockback` | 算出来了（`HitResult.knockback`），但 `applyHits` **只扣血**，没有真的推人 | 击退是死字段，表里的 4~16 全都没有效果 |
| 重击 | `ARCHIVIST_HEAVY` / `NURSE_HEAVY` 在数据里，但原型只把轻击挂到了玩家身上 | **没有任何输入能打出重击** —— 这段取舍现在还没被玩到 |

### 状态机

每个能出招的实体身上挂一个：

```ts
interface ActionState {
  def: ActionDef | null;   // 当前动作
  frame: number;           // 已经推进到第几 tick
  hasHit: Set<string>;     // 这次攻击已经打到过谁（防止一招多段）
}
```

推进规则（每 tick，`actionPhase` 的实际边界）：

```
frame++
if frame < startup                    → 起手中，还没判定
if startup <= frame < startup+active  → 判定期，检查命中
if startup+active <= frame            → 收招中
if frame >= startup+active+recovery   → 动作结束，可以出下一招
```

**实现差异**：上面写的是代码里的边界，比初稿差一 tick（初稿写 `frame <= startup`）。
18 帧的一招因此是 frame 0~5 起手、6~8 判定、9~17 收招。
`rt-combat.test.ts` 的「帧边界」按这个边界逐帧断言，所以这一 tick 有测试钉着。

`hasHit` 是必须的：否则站在判定范围里不动，一招会打出 3 次伤害。

## 七、判定：扇形，不是矩形

```ts
function inHitbox(attacker: Body, dir: Vec2, def: ActionDef, target: Body): boolean {
  const dx = target.x - attacker.x;
  const dy = target.y - attacker.y;
  const dist = Math.hypot(dx, dy);
  if (dist > def.range + target.hw) return false;
  if (def.arc >= 360) return true;
  // 目标方向与出招方向的夹角
  const angle = Math.abs(Math.atan2(dy, dx) - Math.atan2(dir.y, dir.x));
  const diff = Math.min(angle, Math.PI * 2 - angle);
  return diff <= (def.arc / 2) * (Math.PI / 180);
}
```

**为什么用扇形不用矩形**：矩形判定在斜向会露出四个角，
玩家会觉得"明明没碰到却被打了"。扇形天然对称。

**朝向是独立状态**：不是"移动方向"，而是"最后按的方向键"。
移动中转身打背后、站定后回头打 —— 这些都是动作游戏的基本操作。

**实现差异**：命中距离用的是 `range + max(target.hw, target.hh)`，
不是上面代码里的 `range + target.hw` —— 目标自身有体积，不算进去的话"贴着大怪站着反而打不到"。
另外完全重叠（距离 ≈ 0）直接算命中，不判方向。

## 八、敌人 AI：状态机，起手帧即预警

```ts
type AiPhase = 'idle' | 'chase';   // 实际只有这两个
```

```
idle ──看见玩家──→ chase ──进入 attackRange 且冷却为 0──→ 出招（交给 ActionState）
  ↑                  ↑                                          │
  └──玩家太远 / 玩家死了──┴──────────── 冷却走完 ───────────────┘
```

**关键：出招那一段（起手）必须在画面上看得见。**
怪物抬手 → 玩家躲开 → 怪物打空进入收招 → 玩家反击。
这一整条链是动作游戏的全部乐趣。**怪物没有起手帧，游戏就没有博弈。**

**实现差异**：`windup` / `attack` / `recover` **没有做成 AI 的状态**。
它们本来就是 `ActionState` 的 `startup` / `active` / `recovery`（第六节）——
在 AI 里再存一份，等于同一件事有两个状态机，早晚不同步。
渲染层的"抬手预警条"就是直接读 `actionPhase(e.action)` 画出来的。
`hurt` 也没做：受击不会打断动作。

AI 自己新增了两个字段：

| 字段 | 为什么必须有 |
|---|---|
| `cooldown` / `cooldownMax` | 出招后要歇一段。没有它就会贴脸连打，"看抬手"变成没时间做的动作 |
| `stopDistance` | 追到这个距离就停。实体之间不碰撞（第四节），不停下就会和玩家完全重叠 —— 看起来像穿模，还挡住视线 |

出招期间**完全不动**、朝向在**出招瞬间锁死**，这两条是 `ai.ts` 里最要紧的两行：
前者让抬手能被看见，后者让"绕到背后"成为一个真操作 ——
出招中还扭头追人的话，攻击就变成跟踪弹了。

每个敌人在数据里声明（`src/data/rt/enemies.ts`）：

```ts
interface RtEnemyDef {
  id: string; name: string; sprite: string;
  hp: number;
  speed: number;              // 像素/秒
  hw: number; hh: number;     // 半宽半高，没有嵌套的 body
  attack: ActionDef;          // 复用玩家那套帧数据
  detectRange: number;        // 多近开始追
  attackRange: number;        // 多近开始出招
  stopDistance: number;
  cooldown: number;           // 出招后歇多少 tick
  sanDrain: number;           // 靠近时每秒扣多少理智（见第九节）
}
```

| 敌人 | hp | 速度 | 起手 / 判定 / 收招 | 伤害 | 侦测 | 出招距离 | 停距 | 冷却 | sanDrain |
|---|---|---|---|---|---|---|---|---|---|
| 爬行物 | 6 | 62 | 10 / 4 / 14 | 2 | 150 | 20 | 14 | 30 | 0.5 |
| 护工 | 20 | 34 | 26 / 6 / 30 | 6 | 130 | 34 | 24 | 60 | 1.2 |

两者是**刻意互补的**：爬行物快而脆、起手短，逼玩家不能站桩；
护工慢而厚、起手 26 tick（0.43 秒），它的存在就是为了教玩家"看抬手"。
只有前者是纯反应测试，只有后者又太慢。

`sanDrain` 是新的：**怪物的压迫感不只来自伤害，还来自"待在它旁边就掉理智"**。
这让"跑"成为一个真实选项，而不只是"打不过才跑"。

**实现差异**：core 侧的刷怪模板 `SpawnTemplate` 把这些字段原样收着（`ai` 嵌一层），
data → core 的转换是**手写的**：原型 `placeFoe` 写一遍、测试里再写一遍，没有 `toSpawnTemplate()`。
已经漏过一次字段 —— 原型生成的怪**没有传 `sanDrain`**，
所以上面那条"待在它旁边就掉理智"在原型里不生效。

## 九、理智系统

理智 `san` 仍是核心资源，但机制全部重做。

| 项 | 值 |
|---|---|
| 范围 | 0 ~ 100 |
| 上限 | `sanMax`（角色属性，可被 `buff` 改） |
| 自然流失 | 每 `X` 秒 -1（`X` 由楼层深度决定，越深越快） |
| 被怪物靠近 | 每秒 -`sanDrain` |
| 低于阈值 | 有额外惩罚（见下） |
| 恢复 | **只有光和蜡烛** |

**实现差异**（逐条对着代码）：

| 原设计 | 实际 |
|---|---|
| 自然流失"每 X 秒 -1，X 由楼层深度决定，越深越快" | `sanDrainEvery` 是开局定死的 tick 数（默认 720 = 12 秒 1 点），**不随 `depth` 变**；`depth` 目前只有叙事层在读 |
| "低于阈值有额外惩罚" | 没做。低于阈值唯一的变化就是刷怪系数（下一段） |
| "被怪物靠近，每秒 -sanDrain" | 判据是**离怪距离 ≤ 它自己的 `detectRange`**（"它在追你，就是在压迫你"），多只怪各自累加 |
| `sanMax` 可被 `buff` 改 | 成立：`buff` 经活视图写到 `rt.sanMax`，`tickSanity` 每帧夹紧 |
| 恢复只有光和蜡烛 | 成立，而且**取最大值不是求和** —— 求和的话往地上插一排蜡烛就能无限回理智，"蜡烛会烧完"这个代价就形同虚设 |
| 三段计算的顺序 | 写死成"先光照恢复 → 再怪物压迫 → 最后自然流失"。反过来的话恢复永远被下一次流失吃掉，光就成了摆设 |

### 理智下降 → 实时刷怪

**这是"实时刷"的，不是只影响新房间。**

```
下次刷怪间隔 = max(30, 480 / 理智系数(san)) × 抖动(0.6 ~ 1.4)     // 单位：tick
```

**实现差异**：不是"每秒掷一次概率"，是**倒计时**：`spawnTimer` 归零才刷一只，
刷完按上式重设。**没有深度系数**。抖动是刻意的 —— 固定间隔会让玩家数着秒等下一只，节奏就死了；
抖动让"理智在掉"表现为"不知道什么时候又冒出来一只"。
另外两条闸：场上同时最多 12 只（`maxAlive`），以及离玩家 80 px（5 格）以内不许刷
（`findSpawnSpot` 随机试 24 次，试不到就这轮不刷 —— 不做"遍历整张图找最远点"那种事）。

| 理智 | 系数 | 表现 |
|---|---|---|
| 70 ~ 100 | 1.0 | 只有原本就在的怪 |
| 40 ~ 70 | 1.5 | 偶尔从阴影里冒出一只 |
| 10 ~ 40 | 2.0 | 明显变多 |
| 1 ~ 10 | 2.5 | 源源不断 |
| **0** | 3.0 | **地图风格切换** |

**为什么用系数曲线而不是阈值**：阈值会让玩家在 71 和 69 之间感到毫无区别，
而 70 和 69 的实际难度天差地别。曲线让"理智在掉"这件事**一直在被感知**。

**实现差异**：原稿写的是"曲线"，实现是**五档阶梯**（`sanity.ts` 的 `spawnMultiplier`），
理由也换了：一条平滑曲线没人能说出 63.7 点理智该刷几只，
阶梯的数值表策划一眼看得懂、随手能改。档位边界是严格小于：
`san >= 70 → 1.0`、`40 ~ 69 → 1.5`、`10 ~ 39 → 2.0`、`1 ~ 9 → 2.5`、`0 → 3.0`。
"一直在被感知"这层意思保留了下来 —— 跨档那一下的难度差是有意做陡的。

### 理智归零 → 地图风格切换

归零不是死亡，是**世界换了一层皮**：

- **配色**：`assets/map/` 切到 `assets/map/zero/`（同一批瓦片，血肉化配色）
- **地形**：部分墙变成可穿透的血肉，地面长出新东西（待定）
- **怪物**：系数拉满
- **可逆**：回到光里把理智拉回 1 以上，**世界切回来**

**可逆是刻意的。** 不可逆的话"归零"就等于"这局完了"，玩家会直接重开；
可逆的话它变成一个**可以掉进去、也可以爬出来的状态** —— 那才有戏。

**实现差异**：

- **配色做了**，做法是"同一批字符画 + 两套调色板"（`tools/gen-assets.mjs` 的
  `THEME_NORMAL` / `THEME_ZERO`）—— 所以换风格不用画两套图，多加载两份 PNG 就够。
- **地形替换没做**：地形还是地板 / 墙两种，血肉化只体现在颜色上。
- 角色也生成了归零版（`actions/*_zero.png`），但**没人加载** —— 换肤目前只覆盖地图瓦片。
- 判定用 `san <= 0`（`isZeroState`），所以负数是安全的；
  归零 / 复原各发一次 `sanity` 事件，不是每帧都发。

### 恢复：光与蜡烛

理智**只能**靠光恢复。没有"吃药回理智"。

| 光源 | 位置 | 半径 | 恢复速率 | 拿得走 |
|---|---|---|---|---|
| **壁灯** | 固定，长在墙上 | 5 格 | +2 / 秒 | 否 |
| **蜡烛（手持）** | 玩家携带 | 4 格 | +1 / 秒 | 是 |
| **蜡烛（插地）** | 玩家放下 | 6 格 | +3 / 秒 | 否，且**烧得更快** |

蜡烛有**燃料**，按秒消耗，烧完就没了（`assets/map/candle.png` 那根）。

**手持和插地是一个真实取舍**：

- 拿在手里 → 能边走边回，但回得慢
- 插在地上 → 回得快、范围大，**但你得留在这儿，而且它烧得更快**

这个取舍和整个游戏的主题一致：**想要什么，都得拿东西换。**

**实现差异**：

- 三档光源的数值和表一致：壁灯半径 5 格 +2/秒（`fuel = -1`，无限）、
  手持蜡烛半径 4 格 +1/秒（燃料 90 秒，玩家出生就带着）、插地蜡烛半径 6 格 +3/秒。
- 插地的代价**不是"烧得更快"，是插下去那一刻燃料减半**（`fuel: Math.floor(light.fuel / 2)`）。
  效果一样（回得快、留不住），实现更省事：不用给单个光源再加一个"消耗倍率"字段。
- **插地的逻辑写在 UI 层**（`rt-view.ts` 的 `plantCarriedCandle`），
  core 的 `light.ts` 里那个 `plantCandle` 是个**空壳**：它只看"手上有灯且没插过"就返回 `true`，
  既不生成地面光源、也不清空手上的灯，`LightSource.planted` 还是 `readonly`。
  也就是说这条规则现在只有 UI 层能验，core 侧只测得到"手上没蜡烛就插不了"。
- 燃料按 tick 扣（90 秒 = 5400 tick），表里的"每秒"只是给策划看的表述。

## 十、实体与生成

```ts
interface Entity {
  id: string;
  kind: 'player' | 'enemy' | 'item' | 'prop' | 'light';
  body: Body;
  facing: Vec2;
  hp: number;  hpMax: number;   // 实际是必填，不是可选
  speed: number;
  action: ActionState;          // 所有能动的东西都有，包括玩家
  ai?: AiState;                 // 敌人专属：phase / cooldown / cooldownMax / 三个距离
  attack?: ActionDef;           // 能出什么招
  light?: LightSource;          // 壁灯、蜡烛
  sanDrain?: number;            // 待在它旁边每秒扣多少理智
  storyNode?: string;           // 这个物品对应哪段剧情（只有叙事物件有）
  itemDefId?: string;
  alive: boolean;
}
```

`state.entities: Entity[]` 取代原来的 `state.enemies`。
**玩家也是一个 entity**（`kind: 'player'`），这样判定代码只有一套。

**实现差异**：字段比初稿多三个（`attack` / `sanDrain` 也挂在实体上），`hp` 与 `action` 是必填。
`ai` 是完整的参数结构（`types.ts` 的 `makeAiState`），不是 `{ phase, timer }` ——
理由写在代码里：参数挂在 state 上才可存档、可回放、可被内容包改，而不是散在调用处的常量。

实体销毁用 `alive = false` + 每 tick 末尾统一清理，
不在遍历中改数组（这是实时循环里最容易出的 bug）。

### 房间清空

```
连续 90 tick（1.5 秒）一只活着的 kind === 'enemy' 都没有 → 房间清空
```

**实现差异**：上面这条是实际规则。初稿写的是"房间内所有敌人都不见了"——
实时刷怪下那条**永远不成立**：刚打完一只，下一只又冒出来。
为什么是 90 tick、代价是什么，见第十六节第 2 条。

**这条链路完全不变**：清空 → 挑一个剧情节点 → 掉叙事物件 → 拾取 → 全屏剧情 → 选项 → flag。
变的只是"怎么算清空"，从"回合结束时检查"变成"每 tick 检查"。

## 十一、渲染

| 项 | 值 |
|---|---|
| 瓦片 | **16 × 16** px |
| 角色 | **16 × 24** px |
| 房间 | 21 × 15 格 = **336 × 240** px（实际按视口算，见下） |
| 缩放 | **整数倍**（手机 3x，桌面 4x）—— 实际是"优先整数倍"，见下 |

**必须整数倍缩放。** 非整数倍会让像素大小不均匀，
一个像素忽大忽小 —— 像素风最难看的失败方式就是这个。

**一个房间一屏，不滚动。** 房间之间用门连接。

这样做的理由不只是省事：

1. **保住现有地图生成器** —— 它本来就是按"房间"组织的，槽位系统也挂在房间上
2. **一屏 = 一个战斗单元**，玩家一眼看全，不用小地图
3. Isaac / 元气骑士都是这个结构，被验证过

**实现差异**：

- 房间尺寸**不写死 21 × 15**，`planRoom(视口宽, 视口高)` 按屏幕算：11~29 列 × 10~21 行，
  竖屏给竖房间、横屏给横房间，缩放从 6 倍往下试，挑第一个装得下的。
  固定尺寸的后果实测过：竖屏上宽度先卡住缩放，只剩 1 倍，
  336 × 240 的小方块挂在 844 px 高的屏幕上，上下全黑，看起来像"什么都没画出来"。
- **缩放优先整数倍，但放不下时必须允许小数**（`fitCanvas`：`s >= 1 ? Math.floor(s) : Math.max(0.2, s)`）。
  曾经写成 `Math.max(1, Math.floor(s))`，画布比可用空间还大时缩不下去，右侧连人带怪被挤出屏幕。
  宁可像素稍微不齐，也不能有东西看不见 —— 这两条都有回归测试盯着。
- **门还没接**：门与"清完自动开"没有实现，房间之间也没有连接。
  `assets/map/door.png`、`stairs.png`、`floor_stained.png` 都生成了，没人加载。

渲染用 **Canvas 2D**，不用 DOM。原因：
- 每帧要画上百个精灵，DOM 撑不住
- `image-rendering: pixelated` 一行就够
- `assets/README.md` 里"界面按 id 取图，不 import 进 TS"的约定继续有效

## 十四、测试策略

实时游戏的测试比回合制难，但固定时间步把这个难度抹平了。

**核心工具**（实际的名字和签名）：

```ts
/** 喂 n 个 tick 的相同输入，返回期间产生的所有事件。state 在原地被推进 */
function runTicks(state: RtState, input: InputState, count: number): TickEvent[]
```

因为 `DT` 固定、RNG 走 `state.rngState`，而 `tickRt` 只读 `state` 和 `input`
（它**原地改** `state`，不是纯函数 —— 见第十六节第 1 条），
**同一个初始 state + 同一串输入 = 逐帧完全一致的结果。**
要"前后对比"或"从某点分叉"，先 `cloneRtState()` 拷一份。

必测的几类：

| 类型 | 例子 |
|---|---|
| **帧数据边界** | 起手第 5 tick 打不到、第 6 tick 打得到；判定最后 1 tick 还能打到 |
| **命中唯一性** | 一招站在范围内不动，只掉一次血 |
| **确定性** | 同一 seed + 同一输入序列，跑 1000 tick 两次，逐字段比对（浮点要**精确相等**） |
| **确定性（反例）** | 故意多跑 1 tick，state **必须**不同（否则说明 tick 没在做事） |
| **碰撞** | 贴墙走不穿墙、斜向不加速、撞墙贴住格子边缘；**卡角只断言"两轴都被挡住且不瞬移"** —— 代码里没有脱困逻辑，"能被推出"这条没做 |
| **理智** | 归零切换主题、回到光里切回来、刷怪系数随理智单调不增 |
| **不变量** | 任何时刻 `hp >= 0`、`san` 在 `[0, sanMax]`、实体 id 不重复 |

**"反例测试"那一条特别重要**：只测"两次相同跑出相同结果"是不够的 ——
一个什么都没做的 `tick` 也能通过。必须有一条测试证明 **`tick` 真的在推进世界**。
实际上写了两条：多跑一 tick、换一个输入，状态都必须不同。

**实际规模**：实时层 4 个测试文件、**141 个用例**
（`rt` 51 / `rt-combat` 29 / `rt-sanity` 30 / `rt-story` 31）；
另外 `ui-smoke` 里有 4 条原型挂载 / 卸载用例，`dist-smoke` 里有 1 条
"带 `?proto=rt` 冷启动再退出"的用例。整个仓库 8 个文件 284 个用例一起跑，
回合制那套（`engine` / `content`）原样留着并在跑。

**实现差异**：初稿的工具函数叫 `simulate(...): ReduceResult`，签名是空想出来的 ——
`rt-view.ts` 里确实有一个 `simulate`，但它是 `void` 包装、**没有任何调用点**；
测试用的全是 `runTicks`。

| 步 | 当初定的 | 实际产物 | 验收 | 结论 |

### 第 2 步：帧数据战斗

### 第 3 步：理智、光、蜡烛、刷怪、归零

## 十六、计划里没写、做到才发现的问题

这些都不在初稿里。有的是"当时那么写，真做起来不成立"，有的是"做的时候才冒出来的决定"。
每一条都写清楚**为什么**和**代价**。

### 1. `tick` 在原地修改 `state`，不返回新对象

初稿的工程纪律写的是"`tick` 也必须是纯函数"。实际 `tickRt` **原地改 `state`**，
只把事件用返回值交出去 —— 这一点和回合制的 `reduce` 不一样，是有意的：

> 一秒要跑 60 次。每次都深拷整个 state（几十个实体 + 一张地图）会产生大量垃圾，
> 而实时循环对 GC 停顿极其敏感，一次 major GC 就是一帧明显的卡顿。

**代价要说清楚**：

| 代价 | 表现 |
|---|---|
| "上一帧的 state"不再自动留着 | 要前后对比、要从某点分叉，必须先 `cloneRtState()`（测试和回放都走这条路） |
| 顺序错了会直接改坏世界 | `tick` 内部读写同一个对象，"先算后写"写成"边读边写"不会报错，只会在某些帧上数值不对 —— 所以第 7 条的阶段顺序从"风格"变成了"正确性" |
| 事件只能靠返回值传 | 不能靠比对两份 state 反推事件 |
| 克隆容易漏 | `cloneRtState` 里 `hasHit` 必须 `new Set(...)`、`flags` 必须深拷 —— 传引用的话副本上打一下，原件也记成"这一招已经打到过了" |

**确定性没有损失**：`tickRt` 仍然只读 `state`、`input` 和模块常量（`DT`），
同样的输入必然得到同样的结果。"纯函数"这条纪律的实际口径因此改成了
"**只读 state 和 input，不返回新对象**"（见第十九节）。

### 2. "清空房间"必须重新定义：连续 90 tick 没有敌人

初稿写的是"房间内所有 `enemy` 都没了 → 清空"。**实时刷怪下这条永远不成立**：
刚打完一只，下一只又冒出来 —— 于是剧情永远等不到。

现在的定义（`story.ts`）：

```
连续 90 tick（1.5 秒）场上没有活着的 enemy → 房间清空
中间来了一只 → noEnemyTicks 归零，重新数
```

**为什么是 90 tick**：够玩家喘口气、看清地上掉了什么，又不至于等到不耐烦。
这一条同时决定了"叙事物件什么时候掉"，所以它其实是**叙事节奏的节拍器**，
不是纯技术细节。

**注意**：原型里 `spawnTable` 是空的（实时刷怪没接进去），
所以原型里的"清空"实际等于"打完开局那三只、再等 1.5 秒"。

### 3. 叙事层的接法：`narrative-bridge.ts` 的活视图

**问题**：叙事层操作的是 `GameState`（`state.player.san`，嵌套在 `player` 上），
实时层是 `RtState`（`san` 直接挂在 state 上）。字段名和层级都不一样。

**做法**：`narrativeView(rt)` 造一个**全是 getter / setter 的对象**，
读写直接映射回 `RtState`。于是叙事层一行不用改，
读到的永远是当前值，写进去的东西（扣理智、加 flag、改 `phase`）真的落在 `RtState` 上。

**为什么不用"拷贝出去、跑完再拷回来"**：那样每次调用都要同步十几个字段，
**漏一个不会报错**，只在几个小时后表现为"某个结局永远走不到"——
效果看起来生效了，其实写进了临时对象。活视图没有这个窗口期。

**代价也要说清楚**：

| 代价 | 具体是什么 |
|---|---|
| 需要一次 `as unknown as GameState` 强转 | 实时层没有 `floor` / `turn` / `act` 这些回合制专有字段，只能填桩 |
| 桩是空数据 | `player.pos` 恒为 (0,0)、`player.relics` 恒为 `[]`、`act` 恒为 1、`floor` 是个空壳（`rooms: []`、`tiles: []`）—— **叙事层里任何真去读 `floor` 的分支在实时层都拿到空数据**，只能靠"不调用那些函数"来守 |
| 视图绑定的是造它那一刻的玩家实体 | 玩家实体被 `sweep` 清掉之后，`hp` 的读写会静默走 `pe?.hp ?? 0` 这条分支，不报错 |
| 每次都新建 | 视图本身几乎不占内存（一堆 getter）；缓存它反而会在"玩家实体换了"时出错 |

测试专门盯这一条：写进去必须真的落在 `RtState` 上（断言信息就是
"理智没落回去""phase 没落回去 —— 世界不会冻结"）。

### 4. 事件词汇表统一：`tickRt` 返回回合制那套 `GameEvent`

初稿没说实时层的事件长什么样，做的时候必须定。定下来的是
`export type TickEvent = GameEvent`，**不自立一套**。

**为什么**：表现层（`ui-web/render.ts`）已经认识 `GameEvent` 的每一个分支，
实时层再定义一套的话 UI 要写两份渲染逻辑；而且叙事层（`openStory` / `applyEffects` /
`closeStory`）收的就是 `GameEvent` —— 共用一个数组，剧情事件和战斗事件才能走同一条路。

| 实时层实际发的 | 说明 |
|---|---|
| `attack` | 带 `attacker` / `target` / `damage` / `killed`，**不带坐标** —— 那一帧之后目标可能已经被清掉了，位置由 UI 自己查 |
| `message` | 蜡烛烧完 |
| `sanity` | **只在归零 / 复原的切换帧发**，不是每帧都发 |
| `drop` | 叙事物件落地（沿用回合制的掉落事件） |
| `actEnded` | `endRun` 判定结局时发 |

实时层的 `tick` 自己**不发** `moved` / `blocked` / `hurt` / `enemyTurn` / `roomCleared` /
`floorChanged` / `died` —— 这些是回合制那条路径的词汇
（叙事层借同一个数组推出去的事件不受此限：选项里的 `sanity` 效果照样发 `sanity`）。
其中 `died` 特别值得注意：实时层现在**根本没有死亡事件**（见第十八节）。

顺带一个还没收口的地方：离散命令（选选项 / 拾取 / 插蜡烛）**没有统一入口**，
原型里是在 DOM 回调里直接调函数。它们不经过 `tick`，
所以不走固定时间步，也没法被输入回放覆盖。

### 5. 房间尺寸必须跟着屏幕算

初稿写死"房间 21 × 15 格、一屏一房间"。做成固定尺寸的直接后果实测过：
手机竖屏上宽度先卡住缩放，只剩 1 倍，336 × 240 的小方块挂在 844 px 高的屏幕上，
上下全黑 —— 表现就是"进去什么都没画出来"。

现在 `planRoom(视口宽, 视口高)` 从 6 倍缩放往下试，挑第一个装得下的：
列 11~29、行 10~21，竖屏给竖房间、横屏给横房间；
`fitCanvas` 在尺寸变化时只重算缩放，**不重新规划房间**（那等于把这一局重置了）。

同一件事还牵出两条：缩放**优先整数倍但放不下时必须允许小数**，
以及房间尺寸一变，**所有硬编码的格子坐标都会落到墙里或墙外**。

### 6. 一切"按坐标摆东西"都要能安全化

房间尺寸是算出来的，所以"把敌人放在第 10 行第 10 列"在窄屏上会落进墙里 ——
表现是"这个敌人不见了"，而且不报任何错。

`findOpenCell(map, tx, ty)` 因此归 core：一圈圈往外找最近的地板，
同圈按扫描顺序（结果确定，回放不会分叉）。敌人、叙事物件、壁灯、
插地的蜡烛全都走它；测试断言的是**不变量**：任何格子输入，输出都不是墙。

放 core 而不是界面的理由很实在：**放进 core 才能被测试覆盖，
放在界面里就只能靠眼睛看，而眼睛看不出来**。

### 7. `tick` 内部九个阶段的顺序是正确性，不是风格

```
① 推帧 → ② 决策（玩家输入 / 敌人 AI）→ ③ 位移 → ④ 命中 → ⑤ 光
→ ⑥ 理智 → ⑦ 刷怪 → ⑧ 清空判定与叙事触发 → ⑨ 清理死实体
```

| 顺序 | 为什么不能换 |
|---|---|
| ① 在 ② 之前 | 让"这一帧刚开始的动作"从 frame 0 算起。反过来的话起手帧凭空少一帧，边界测试也没法解释 |
| ④ 在 ③ 之后 | 判定要用**这一帧移动完之后**的位置。反过来的话，冲进攻击范围的那一帧打不到人 |
| ⑧ 在判定之后 | 这一帧刚被打死的敌人要算进"没了"，否则最后一只怪死的那一帧计数还是旧的 |
| ⑨ 最后 | 统一 `sweep` 清死掉的实体 —— **不在遍历中改数组**，那是实时循环最经典的 bug（跳过元素或索引越界，还不一定每次复现） |
| `phase !== 'playing'` | `tickRt` 第一行就返回，什么都不跑。剧情期间读多久都不影响数值 |

## 十九、工程纪律（在 `01` 的基础上修订）

`01` 的第五条纪律有两条要改（其中一条是"口径改了"，不是"规矩没了"），其余继续有效。

| 原纪律 | 现在 |
|---|---|
| `core` 里禁止 DOM | **不变**。`rt/` 里也不许出现 `requestAnimationFrame` —— 那是外壳的事，`core` 只管 `tick` |
| 禁止 `Math.random()` | **不变**，且更重要了：一秒跑 60 次，任何一处漏网的 `Math.random` 都会让两条路迅速分岔 |
| `reduce` 是纯函数 | **改**：`tick` **不返回新 state**，它在原地改（第十六节第 1 条）。口径变成"**`tick` 只读 `state` 和 `input`，不读模块外的任何东西，也不返回新对象**"；要前后对比先 `cloneRtState()` |
| 所有输入只产出 `Intent` | **改**：连续量产出 `InputState`；离散量在实时层**没有统一通道** —— 选选项 / 拾取 / 插蜡烛是普通函数，原型里由 DOM 回调直接调。这是要收口的地方（见第十八节） |
| 内容里禁止代码 | **不变** |

新增两条：

7. **所有计时用 tick，不用秒。**
   写 `startup: 6` 不写 `startup: 0.1`。
   浮点秒累加会漂移，而帧数必须是精确整数 —— 否则"第 6 帧"和"第 7 帧"会随帧率变化。
   **例外是速率量**：理智恢复 `rate`、`sanDrain` 的单位是"每秒"（给策划看的表述），
   燃料、帧数、间隔一律 tick。这条划分写在 `types.ts` 的 `LightSource` 注释里。

8. **往外发的事件用回合制那套 `GameEvent`，不自立一套。**
   理由见第十六节第 4 条：表现层和叙事层已经认识这套词汇，
   另起一套就要写两份渲染逻辑，而且剧情事件会和战斗事件分家。
