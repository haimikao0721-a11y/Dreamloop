# 06 · 实时架构

> 同一栋楼，同一些字。换的是"怎么走、怎么打"。

这一篇定实时化的技术骨架。**叙事层、内容格式、结局判定一行不改** ——
换掉的是地图、移动、战斗、输入、渲染五层。

`01-核心循环.md` 里的三层解耦、叙事槽位、flag 收敛、死亡即叙事**全部继续有效**，
只有「回合制」这一条作废。

---

## 一、为什么改，代价是什么

**改的原因**：格子回合制的操作感是"点一下走一步"，玩家要的是"推着走"。

**代价要说清楚**，因为这次要废掉的东西里有四轮平衡试错换来的成果：

| 作废 | 保留 |
|---|---|
| `combat.ts` 全部 | 叙事层（槽位 / 节点 / 选项 / flag / 结局） |
| `engine.ts` 的回合部分 | 内容数据（角色 / 物品 / 剧情 / 结局） |
| 地图的格子移动 | 条件与效果词汇表 |
| 撞上去就打的战斗 | 死亡即叙事、幕级存档 |
| 前面调的平衡数值 | `assets/` 素材管线 |
| 约一半测试 | 三个模式的架构 |

**一句话**：死掉的是"怎么打"，活着的是"打完之后发生什么"。
而后者才是这个项目的卖点。

---

## 二、核心循环：`tick` 与 `reduce` 并存

这是整篇最重要的一个决定。

```
tick(state, input, dt)  → { state, events }     // 一秒 60 次，连续模拟
reduce(state, intent)   → { state, events }     // 玩家按下的那一下，离散命令
```

**为什么不把 `reduce` 也吃掉**：因为"选哪个选项""用哪件道具""下不下楼"这些
**本来就不是连续量**。硬塞进 `tick` 会让每一帧都在判断"玩家是不是又按了一次选择"，
是把简单问题复杂化。

分工：

| 走哪条 | 管什么 | 例子 |
|---|---|---|
| `tick` | **时间在流动的东西** | 移动、敌人 AI、攻击帧推进、理智流失、蜡烛燃烧、刷怪 |
| `reduce` | **玩家按下的那一下** | 选择选项、使用道具、下楼、交互、开关菜单 |

```
phase: 'playing'  →  tick 推进，reduce 收全部离散命令
phase: 'story'    →  tick 冻结，reduce 只收 choose
phase: 'dead'     →  tick 冻结，reduce 只收 restartAct
```

`phase !== 'playing'` 时**模拟整个冻结** —— 这正是"停住操作是规则"那条
（见 `05-表现与文字.md`）。

**顺带解决一个隐患**：剧情期间不模拟，所以"玩家读了多久"不影响任何数值。
"动画时长拖进种子复现"这个问题被结构性地排除了，不需要额外约定。

## 三、固定时间步：确定性的地基

```ts
const TICK_RATE = 60;         // 每秒 60 次模拟
const DT = 1 / TICK_RATE;     // 每次固定 1/60 秒，永远是同一个值
```

**渲染帧率不等于模拟帧率。** 外面累加真实时间，够一个 `DT` 就跑一次 `tick`：

```
累加器 += 这一帧真实经过的时间
while (累加器 >= DT) { tick(state, input, DT); 累加器 -= DT; }
渲染(state)        // 可能一帧跑 0 次、1 次或 2 次 tick
```

**为什么必须固定步长**：浮点运算不满足结合律，`(a+b)+c !== a+(b+c)`。
如果 `dt` 随帧率浮动，同一个 seed 在 60Hz 手机和 120Hz 手机上会走出**不同的结果** ——
神种分享、bug 复现、回放录像全部失效。

固定 `DT` 之后：**同一份 seed + 同一条输入时间轴 = 完全相同的一局。**
这是本项目从回合制继承下来的最重要的一条资产，不能丢。

| 项 | 值 |
|---|---|
| 模拟频率 | 60 Hz，固定 |
| 单次上限 | 一帧最多补 5 次 tick（防止卡顿后"追帧"雪崩） |
| 用整数存的量 | 一切帧数、计时器（单位：tick） |
| 用浮点存的量 | 只有坐标、速度、朝向 |

## 四、坐标与碰撞

**单位用像素**（不是格）。一格 = 16 px。

```ts
interface Vec2 { x: number; y: number }

interface Body {
  x: number; y: number;      // 中心点，浮点
  hw: number; hh: number;    // 半宽半高（AABB）
  vx: number; vy: number;    // 速度，像素/秒
}
```

**为什么用中心点 + 半宽半高**：翻墙、卡角、贴边这些 bug 全都出在
"矩形四条边怎么和别的矩形比"。用中心点表示，判定就一行：

```ts
const hit = Math.abs(a.x - b.x) < a.hw + b.hw
         && Math.abs(a.y - b.y) < a.hh + b.hh;
```

### 碰撞分层

| 层 | 挡谁 | 说明 |
|---|---|---|
| **墙** | 所有人 | 地形，`TileKind` 为 `wall` |
| **门** | 所有人 | 房间没清完时是关的，清完自动开 |
| **实体** | 不挡 | 玩家和怪物**互相穿过**，只有攻击判定 |

**实体不互相碰撞**是刻意的：实时动作游戏里怪物互相挤会把玩家卡死，
而且"被一坨怪堵在墙角"是纯粹的挫败，不产生任何决策。
Isaac / 元气骑士都是这么做的。

### 移动

```ts
// 输入向量已经归一化，长度 ≤ 1（摇杆可以推一半 = 走一半）
body.x += input.moveX * speed * DT;
body.y += input.moveY * speed * DT;
```

**斜向不加速**：输入向量先归一化。不做的话斜着走快 41%，玩家会一直斜着走。

## 五、输入：摇杆向量

`Intent` 里那个 `move` 带方向枚举的写法作废。新的是**连续向量**：

```ts
interface InputState {
  moveX: number;    // -1 ~ 1
  moveY: number;    // -1 ~ 1
  attack: boolean;  // 边沿触发：只在按下的那一 tick 为 true
  use: boolean;     // 拾取 / 交互
}
```

四种输入源都产出同一个 `InputState`：

| 设备 | moveX/moveY 怎么来 | 力度 |
|---|---|---|
| **手机轮盘** | 触点相对轮盘中心的偏移 | **有**（推一半走一半） |
| 键盘 | WASD / 方向键，归一化 | 无（只有 0 或 1） |
| 手柄 | 左摇杆原始值 | **有** |
| 鼠标 | 按住时朝指针方向 | 无 |

**轮盘用力度、键盘不用**是必然的：键盘没有模拟量。
所以**任何玩法都不能依赖"力度"**（比如"轻推是潜行"），否则键盘玩家玩不了。

**`attack` 必须边沿触发**。按住不放每帧都是 `true` 的话，
攻击会在收招结束的瞬间自动接下一次 —— 变成"按住就自动打"，
起手帧的意义就没了。

## 六、帧数据：动作定义

全部以 **tick** 为单位（60 tick = 1 秒）。

```ts
interface ActionDef {
  id: string;
  startup: number;     // 起手帧：按下 → 判定出现
  active: number;      // 判定帧：能打到人的窗口
  recovery: number;    // 收招帧：判定结束 → 能动
  // 判定形状（见第七节）
  range: number;       // 攻击距离，像素
  arc: number;         // 扇形角度（度）。360 = 全方位
  damage: number;
  knockback: number;   // 击退距离，像素
  moveX: number;       // 出招时的位移（冲刺攻击用），像素
  moveY: number;
}
```

三段帧的含义**不是数值，是给玩家的信息**：

| 阶段 | 玩家看到什么 | 设计意图 |
|---|---|---|
| **起手** | 武器抬起来 | **这是"能躲"的窗口。** 没有起手 = 玩家只能靠反应，不是靠读 |
| **判定** | 武器扫过去 | 只有这一段能打到人 |
| **收招** | 武器垂下去 | **这是"打空要付代价"的窗口。** 没有收招 = 无脑连按最优 |

**起手和收招是这套系统存在的全部理由。** 只有判定帧的话，
这游戏就退化成"谁按得快谁赢"。

### 初值（待试玩调整）

| 动作 | 起手 | 判定 | 收招 | 合计 | 范围 | 伤害 |
|---|---|---|---|---|---|---|
| 记梦者 · 轻击 | 6 | 3 | 9 | 18 (0.30s) | 20 | 3 |
| 记梦者 · 重击 | 14 | 5 | 20 | 39 (0.65s) | 28 | 7 |
| 值夜护士 · 轻击 | 8 | 4 | 11 | 23 (0.38s) | 18 | 4 |
| 值夜护士 · 重击 | 18 | 6 | 24 | 48 (0.80s) | 24 | 9 |

**两个角色的差别不在伤害，在帧数**：

- **记梦者**：起手快、范围大、**伤害低**。靠"打一下就撤"活着。
  和它"瘦、脆、理智高"的定位一致。
- **值夜护士**：起手慢、范围小、**伤害高、收招长**。每一次出手都是赌博。
  和它"稳、能扛、理智低"的定位一致。

**为什么轻击重击要差这么多帧**：如果轻击全面优于重击，重击就是废字段。
差距必须大到"面对快速怪只能轻击、面对大怪必须重击"。

### 状态机

每个能出招的实体身上挂一个：

```ts
interface ActionState {
  def: ActionDef | null;   // 当前动作
  frame: number;           // 已经推进到第几 tick
  hasHit: Set<string>;     // 这次攻击已经打到过谁（防止一招多段）
}
```

推进规则（每 tick）：

```
frame++
if frame <= startup              → 起手中，还没判定
if startup < frame <= startup+active  → 判定期，检查命中
if frame > startup+active        → 收招中
if frame >= startup+active+recovery   → 动作结束，可以出下一招
```

`hasHit` 是必须的：否则站在判定范围里不动，一招会打出 3 次伤害。

## 七、判定：扇形，不是矩形

```ts
function inHitbox(attacker: Body, dir: Vec2, def: ActionDef, target: Body): boolean {
  const dx = target.x - attacker.x;
  const dy = target.y - attacker.y;
  const dist = Math.hypot(dx, dy);
  if (dist > def.range + target.hw) return false;
  if (def.arc >= 360) return true;
  // 目标方向与出招方向的夹角
  const angle = Math.abs(Math.atan2(dy, dx) - Math.atan2(dir.y, dir.x));
  const diff = Math.min(angle, Math.PI * 2 - angle);
  return diff <= (def.arc / 2) * (Math.PI / 180);
}
```

**为什么用扇形不用矩形**：矩形判定在斜向会露出四个角，
玩家会觉得"明明没碰到却被打了"。扇形天然对称。

**朝向是独立状态**：不是"移动方向"，而是"最后按的方向键"。
移动中转身打背后、站定后回头打 —— 这些都是动作游戏的基本操作。

## 八、敌人 AI：状态机，起手帧即预警

```ts
type AiPhase = 'idle' | 'chase' | 'windup' | 'attack' | 'recover' | 'hurt';
```

```
idle ──看见玩家──→ chase ──进入攻击距离──→ windup ──起手帧走完──→ attack
  ↑                  ↑                                            │
  └──玩家太远─────────┴──────────── recover ←──收招帧走完──────────┘
```

**关键：`windup` 就是起手帧，而且必须在画面上看得见。**
怪物抬手 → 玩家躲开 → 怪物打空进入收招 → 玩家反击。
这一整条链是动作游戏的全部乐趣。**怪物没有起手帧，游戏就没有博弈。**

每个敌人在数据里声明：

```ts
interface EnemyDef {
  hp: number;
  speed: number;              // 像素/秒
  body: { hw: number; hh: number };
  attack: ActionDef;          // 复用玩家那套帧数据
  detectRange: number;        // 多近开始追
  attackRange: number;        // 多近开始起手
  sanDrain: number;           // 靠近时每秒扣多少理智（见第九节）
}
```

`sanDrain` 是新的：**怪物的压迫感不只来自伤害，还来自"待在它旁边就掉理智"**。
这让"跑"成为一个真实选项，而不只是"打不过才跑"。

## 九、理智系统

理智 `san` 仍是核心资源，但机制全部重做。

| 项 | 值 |
|---|---|
| 范围 | 0 ~ 100 |
| 上限 | `sanMax`（角色属性，可被 `buff` 改） |
| 自然流失 | 每 `X` 秒 -1（`X` 由楼层深度决定，越深越快） |
| 被怪物靠近 | 每秒 -`sanDrain` |
| 低于阈值 | 有额外惩罚（见下） |
| 恢复 | **只有光和蜡烛** |

### 理智下降 → 实时刷怪

**这是"实时刷"的，不是只影响新房间。**

```
每秒刷怪概率 = 基础值 × 理智系数(san) × 深度系数(floor)
```

| 理智 | 系数 | 表现 |
|---|---|---|
| 70 ~ 100 | 1.0 | 只有原本就在的怪 |
| 40 ~ 70 | 1.5 | 偶尔从阴影里冒出一只 |
| 10 ~ 40 | 2.0 | 明显变多 |
| 1 ~ 10 | 2.5 | 源源不断 |
| **0** | 3.0 | **地图风格切换** |

**为什么用系数曲线而不是阈值**：阈值会让玩家在 71 和 69 之间感到毫无区别，
而 70 和 69 的实际难度天差地别。曲线让"理智在掉"这件事**一直在被感知**。

### 理智归零 → 地图风格切换

归零不是死亡，是**世界换了一层皮**：

- **配色**：`assets/map/` 切到 `assets/map/zero/`（同一批瓦片，血肉化配色）
- **地形**：部分墙变成可穿透的血肉，地面长出新东西（待定）
- **怪物**：系数拉满
- **可逆**：回到光里把理智拉回 1 以上，**世界切回来**

**可逆是刻意的。** 不可逆的话"归零"就等于"这局完了"，玩家会直接重开；
可逆的话它变成一个**可以掉进去、也可以爬出来的状态** —— 那才有戏。

### 恢复：光与蜡烛

理智**只能**靠光恢复。没有"吃药回理智"。

| 光源 | 位置 | 半径 | 恢复速率 | 拿得走 |
|---|---|---|---|---|
| **壁灯** | 固定，长在墙上 | 5 格 | +2 / 秒 | 否 |
| **蜡烛（手持）** | 玩家携带 | 4 格 | +1 / 秒 | 是 |
| **蜡烛（插地）** | 玩家放下 | 6 格 | +3 / 秒 | 否，且**烧得更快** |

蜡烛有**燃料**，按秒消耗，烧完就没了（`assets/map/candle.png` 那根）。

**手持和插地是一个真实取舍**：

- 拿在手里 → 能边走边回，但回得慢
- 插在地上 → 回得快、范围大，**但你得留在这儿，而且它烧得更快**

这个取舍和整个游戏的主题一致：**想要什么，都得拿东西换。**

## 十、实体与生成

```ts
interface Entity {
  id: string;
  kind: 'player' | 'enemy' | 'item' | 'prop' | 'light';
  body: Body;
  facing: Vec2;
  hp?: number;
  action?: ActionState;
  ai?: { phase: AiPhase; timer: number };
  light?: { radius: number; rate: number; fuel: number };
  alive: boolean;
}
```

`state.entities: Entity[]` 取代原来的 `state.enemies`。
**玩家也是一个 entity**（`kind: 'player'`），这样判定代码只有一套。

实体销毁用 `alive = false` + 每 tick 末尾统一清理，
不在遍历中改数组（这是实时循环里最容易出的 bug）。

### 房间清空

```
房间内所有 kind === 'enemy' 且 alive 的实体都没了 → 房间清空
```

**这条链路完全不变**：清空 → 触发叙事槽位 → 掉叙事物件 → 拾取 → 全屏剧情 → 选项 → flag。
变的只是"怎么算清空"，从"回合结束时检查"变成"每 tick 检查"。

## 十一、渲染

| 项 | 值 |
|---|---|
| 瓦片 | **16 × 16** px |
| 角色 | **16 × 24** px |
| 房间 | 21 × 15 格 = **336 × 240** px |
| 缩放 | **整数倍**（手机 3x，桌面 4x） |

**必须整数倍缩放。** 非整数倍会让像素大小不均匀，
一个像素忽大忽小 —— 像素风最难看的失败方式就是这个。

**一个房间一屏，不滚动。** 房间之间用门连接。

这样做的理由不只是省事：

1. **保住现有地图生成器** —— 它本来就是按"房间"组织的，槽位系统也挂在房间上
2. **一屏 = 一个战斗单元**，玩家一眼看全，不用小地图
3. Isaac / 元气骑士都是这个结构，被验证过

渲染用 **Canvas 2D**，不用 DOM。原因：
- 每帧要画上百个精灵，DOM 撑不住
- `image-rendering: pixelated` 一行就够
- `assets/README.md` 里"界面按 id 取图，不 import 进 TS"的约定继续有效

## 十二、分层：什么保留，什么重写

```
┌─ 元叙事层 Meta ──────────────────────────────┐  ✅ 不变
└──────────────────────────────────────────────┘
┌─ 叙事层 Narrative ───────────────────────────┐  ✅ 不变
│  槽位 / 节点 / 选项 / 条件 / 效果 / 结局       │
└──────────────────────────────────────────────┘
┌─ 地牢层 Dungeon ─────────────────────────────┐  🔄 重写
│  实时模拟 / 碰撞 / 帧数据战斗 / 敌人 AI        │
└──────────────────────────────────────────────┘
```

**叙事层不用改一行代码**，因为它本来就是事件驱动的：
它只关心"房间清空了"和"玩家选了 A"，不关心这两件事是怎么发生的。

新增一层：

```
┌─ 光照层 Light ───────────────────────────────┐  🆕
│  光源半径、理智恢复、蜡烛燃料                  │
└──────────────────────────────────────────────┘
```

**旧文件先留着不删**（`combat.ts` / 旧 `engine.ts`），
等新引擎跑通再一次性移除 —— 这样中途能随时对照。

## 十四、测试策略

实时游戏的测试比回合制难，但固定时间步把这个难度抹平了。

**核心工具**：

```ts
/** 喂 n 个 tick 的相同输入，返回最终状态和期间产生的所有事件 */
function simulate(state: GameState, input: InputState, ticks: number): ReduceResult
```

因为 `DT` 固定、RNG 走 `state.rngState`、`tick` 是纯函数，
**同一个初始 state + 同一串输入 = 逐帧完全一致的结果。**

必测的几类：

| 类型 | 例子 |
|---|---|
| **帧数据边界** | 起手第 5 tick 打不到、第 6 tick 打得到；判定最后 1 tick 还能打到 |
| **命中唯一性** | 一招站在范围内不动，只掉一次血 |
| **确定性** | 同一 seed + 同一输入序列，跑 1000 tick 两次，state 深比对相等 |
| **确定性（反例）** | 故意多跑 1 tick，state **必须**不同（否则说明 tick 没在做事） |
| **碰撞** | 贴墙走不穿墙、斜向不加速、卡角能被推出 |
| **理智** | 归零切换主题、回到光里切回来、刷怪系数随理智单调递增 |
| **不变量** | 任何时刻 `hp >= 0`、`san` 在 `[0, sanMax]`、实体 id 不重复 |

**"反例测试"那一条特别重要**：只测"两次相同跑出相同结果"是不够的 ——
一个什么都没做的 `tick` 也能通过。必须有一条测试证明 **`tick` 真的在推进世界**。

## 十五、迁移计划

分四步，**每步结束时游戏都是可跑的**。

| 步 | 做什么 | 验收 |
|---|---|---|
| **1** | 建 `rt/` 骨架：`loop` / `input` / `physics`，玩家能在空房间里推着走 | 能在屏幕上推着走，穿不过墙 |
| **2** | 帧数据战斗 + 一个会追会打的敌人 | 起手能看见、能躲、能反击 |
| **3** | 理智 + 光 + 蜡烛 + 实时刷怪 + 归零换肤 | 理智机制完整可玩 |
| **4** | 接回叙事层（清房间掉物品 → 剧情 → 选项 → flag → 结局） | 跑通完整链路，删掉旧 `combat.ts` |

**第 4 步之前不删任何旧代码。** 叙事层那边一行都不用改，
所以第 4 步理论上只是"把触发点从回合结束换成每 tick 检查"。

## 十六、工程纪律（在 `01` 的基础上修订）

`01` 的第五条纪律有两条要改，其余继续有效。

| 原纪律 | 现在 |
|---|---|
| `core` 里禁止 DOM | **不变**。`rt/` 里也不许出现 `requestAnimationFrame` —— 那是外壳的事，`core` 只管 `tick` |
| 禁止 `Math.random()` | **不变**，且更重要了 |
| `reduce` 是纯函数 | **扩展**：`tick` 也必须是纯函数（除 `state` 和 `input` 外不读任何东西） |
| 所有输入只产出 `Intent` | **改**：连续量产出 `InputState`，离散量仍产出 `Intent` |
| 内容里禁止代码 | **不变** |

新增一条：

7. **所有计时用 tick，不用秒。**
   写 `startup: 6` 不写 `startup: 0.1`。
   浮点秒累加会漂移，而帧数必须是精确整数 —— 否则"第 6 帧"和"第 7 帧"会随帧率变化。
