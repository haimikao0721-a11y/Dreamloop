# 04 · 社区扩展规范

> 这份文档定义「原版」和「社区内容包」之间的契约。
> 目标：任何人能写一个内容包，不碰引擎代码，也不用担心撞坏别人的东西。

---

## 一、为什么要有这份规范

内容驱动的开源游戏，最容易死在两件事上：

1. **撞 id** —— 两个作者都写了 `goblin`，后加载的把先加载的覆盖了，没人知道为什么
2. **越权** —— 某个 mod 写了"所有人都复活"，把官方八小时的叙事意图一笔抹掉

规范就是防这两件事的。它同时是**给作者的自由**和**给作品的护栏**。

---

## 二、命名空间

### 规则

| 位置 | 写法 |
|---|---|
| 内容包自己的 `namespace` | 必填，短小写，全局唯一 |
| 包**内部**引用自己的内容 | 裸 id，如 `goblin` |
| 包**引用别的包**的内容 | 带前缀，如 `core:returning_coin` |

```ts
export const ABYSS_PACK: ContentPack = {
  id: 'abyss_echo',
  name: '深渊回响',
  version: '1.0.0',
  namespace: 'abyss',        // ← 你的所有内容都活在这个命名空间下
  stories: [...],
};
```

### 查找顺序

引擎按**包加载顺序**查找，靠前的优先：

```
loadPacks([社区包, core])   → 社区包同名 id 覆盖 core
loadPacks([core, 社区包])   → core 优先，社区包只补新内容
```

**这是 mod 覆盖原版内容的唯一机制**，不需要额外的"覆盖声明"。

### 实践建议

- 加**新**内容时不要复用原版 id，用你自己的命名
- 想**改**原版内容时，才故意用同名 id 去覆盖
- 永远不要依赖"另一个 mod 的内容"—— 你不知道玩家装没装它，除非在 `requires` 里声明

## 三、世界律（不可覆盖）

这是本作最重要的一条护栏。

### 问题

官方内容只做绝望线：**第一幕结束时所有角色都会死。**
如果放任社区写"完美救赎线把所有人复活"，官方 8 小时的叙事意图就被一笔抹掉了。

### 解法：把"什么是不可能的"也做成数据

```ts
/**
 * 世界律 —— mod 不许覆盖的硬约束。
 *
 * 这些不是"设定文档"，是引擎和内容校验器都会强制执行的规则。
 */
export interface WorldLaw {
  readonly id: string;
  /** true 表示 mod 不许覆盖；校验器会直接拒绝带冲突声明的包 */
  readonly immutable: boolean;
  readonly desc: string;
}

export const WORLD_LAWS: readonly WorldLaw[] = [
  { id: 'the_dead_cannot_return', immutable: true, desc: '死者不归' },
  { id: 'every_role_dies',        immutable: true, desc: '第一幕结束时所有角色都会死' },
  { id: 'no_victory_endings',     immutable: true, desc: '官方视角下不存在胜利结局' },
];
```

内容包里如果出现 `violates: ['the_dead_cannot_return']` 的结局，
校验器会**拒绝加载整个包**并给出明确错误。

### 但这不等于限制创作

社区能做的比"写好结局"有意思得多：

| ❌ 越权 | ✅ 合规且更有价值 |
|---|---|
| 所有人都复活 | 你救下了某个人，代价是另一个人 |
| 找到出口逃出去 | 你找到了出口，但门只能从外面开 |
| 打败最终 Boss | 你打赢了，然后发现自己成了下一个 Boss |
| 治好所有人的病 | 你治好了他们，但他们不记得自己是谁了 |

**方向是「探索死亡的意义」，不是「否定死亡」。**

这样社区创作**增强**主题，而不是拆台 —— 而且留白本身就是最好的创作邀请。

## 四、内容包清单

```yaml
# packs/abyss_echo/pack.yaml
id: abyss_echo
name: 深渊回响
version: 1.0.0        # 语义化版本
namespace: abyss
requires:             # 依赖声明
  - "core >= 0.1.0"
load_after:           # 加载顺序提示
  - core
```

**依赖必须显式声明**，因为：
- 引擎没法猜你引用了哪些包的内容
- 玩家装的 mod 组合千奇百怪，缺依赖时要能给出人话错误
- 校验器靠它决定"该在哪些包里找 id"

版本约束用语义化版本：
- `core >= 0.1.0` —— 至少要这个版本
- `core ^0.1.0` —— 兼容范围内的任意版本

## 五、提交前自查

跑一条命令：

```bash
pnpm validate
```

它会检查（36 项，含平衡与节奏）：

| 类别 | 检查 |
|---|---|
| 引用完整性 | 所有 `storyNode` / `drop.pool` / `giveItem` / `startItems` 指向真实 id |
| 类型一致 | 掉落声明的 `kind` 与实际物品的 `kind` 相符 |
| 角色门控 | 所有 `requiresTag` 真存在于某个角色；每个节点至少留一个非门控选项 |
| 结局可达 | 结局依赖的 flag 都有人写；存在 `requires: []` 的兜底结局 |
| 结构 | 每个剧情节点至少 1 个选项；正文长度 40~400 字；id 全局唯一 |
| **平衡** | 任一角色中位死亡 ≤ 5 次；两角色难度差 ≤ 4 倍 |
| **节奏** | 单局回合数落在合理区间；平均至少读到 3 段剧情 |

最后两类是**给 mod 作者准备的**：如果你加了一堆超强怪，
平衡守卫会直接告诉你"某个角色现在没法玩了"，而不是等玩家来骂。

## 六、校验器要抓的三类错

### 1. 静默失效（最危险）

引用错一个 id，引擎**不会崩** —— 所有查找都返回 `undefined` 并且被兜住了。
结果是那段内容永远不出现，而作者以为写好了。

> 这是内容驱动项目最典型的失败模式，也是 `pnpm validate` 存在的首要理由。

### 2. 卡死

剧情节点没有选项、所有选项都带 `requiresTag` 而当前角色没有那个 tag ——
玩家会卡在剧情层出不来。

### 3. 世界律冲突

包声明了与 `immutable` 世界律冲突的内容。直接拒绝加载，
而不是"加载了但那条结局永远走不到"。

## 七、给作者的建议

### 从"重写一段剧情"开始，不要从"加一个新角色"开始

改一段已有的剧情、加一个选项、加一个结局 —— 这些改动的验证成本最低，
而且能立刻看到效果。

### 引用原版内容比自己造更划算

原版已经有 `knows_the_name`、`carries_the_coin` 这些 flag 和它们背后的剧情。
把新内容挂在已有的 flag 上，比另起一套状态体系更容易和原版融合。

### 写 `hint`

```ts
{ id: 'my_ending', ..., hint: '在还清醒的时候念出那个名字' }
```

结算界面的「你还有 N 条路没有走到」靠它驱动重开率 ——
**这是内容作者对重开率影响最大的一个字段**，而且只写一句话。

写法：说**玩家该做什么**，不要暴露内部 flag 名。

```
✅ '在还清醒的时候念出那个名字'
❌ '需要 knows_the_name = true'
```

### 分支写在 flag 里，不要写在流程里

```
❌ 选择 A → 节点 1 → 选择 B → 节点 2 → ...   （内容量指数爆炸）
✅ 选择 → setFlag → 结局按条件集合判定        （线性增长）
```

详细规范见 [`02-数据字典.md`](02-数据字典.md) 第十节。

这是给早期贡献者的路径 —— 等 mod 加载机制做完，这些内容可以原样搬进独立内容包。
