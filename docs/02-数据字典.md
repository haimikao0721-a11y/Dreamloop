# 02 · 数据字典（内容作者手册）

> 这份文档是给**写内容的人**看的，不是给写引擎的人看的。
> 你只需要写 YAML / TS 数据，不需要碰任何逻辑代码。

---

## 一、内容包结构

一个内容包是一个 `ContentPack` 对象。原版是 `core` 包，社区扩展是独立包。

```ts
interface ContentPack {
  id: string;          // 包 id，全局唯一
  name: string;        // 显示名
  version: string;     // 语义化版本
  namespace: string;   // 命名空间，防止 mod 撞 id
  roles?: RoleDef[];
  enemies?: EnemyDef[];
  items?: ItemDef[];
  stories?: StoryNode[];
  acts?: ActDef[];
}
```

**id 规范**：小写蛇形，英文 id + 中文 `name`。
例如 `{ id: 'torn_case_notes', name: '撕裂的病历 · 第三页' }`。

---

## 二、角色 `RoleDef`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一 id |
| `name` | string | 显示名 |
| `desc` | string | 1~2 句，要能让人产生选择欲望 |
| `hp` / `san` | number | 初始生命 / 理智 |
| `atk` / `def` | number | 攻击 / 防御 |
| `tags` | string[] | **剧情门控的核心**，见下 |
| `startItems` | string[] | 起始物品 id |

### tags 是角色差异化的全部机制

```ts
{ id: 'dream_archivist', tags: ['scholar', 'lucid', 'frail'],  hp: 16, san: 30, atk: 3, def: 1 }
{ id: 'ward_nurse',      tags: ['healer', 'believer', 'steadfast'], hp: 26, san: 18, atk: 6, def: 2 }
```

剧情选项用 `requiresTag` 引用这些 tag，**两个角色就会看到不同的选项**。

**硬性要求**：
- 两个角色的 tag 集合**不应重合**，否则分叉会被削弱
- 数值要有取舍：理智高的角色战斗属性应该低，反之亦然

---

## 三、怪物 `EnemyDef`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `name` / `glyph` | string | glyph 是单字符显示符号 |
| `hp` / `atk` / `def` | number | 战斗数值 |
| `ai` | `'idle' \| 'aggressive'` | aggressive 会主动追玩家 |
| `tags` | string[] | 供条件判定用 |
| `minDepth` | number | 从第几层开始出现 |
| `drop` | DropEntry[] | 掉落表 |

### 掉落表

```ts
drop: [{ kind: 'consumable', pool: ['herb', 'tonic'], weight: 3 }]
```

- `kind` 必须和 `pool` 里物品实际的 `kind` **一致**（有测试会检查）
- `weight` 是相对权重，不是概率

---

## 四、物品 `ItemDef`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `name` | string | |
| `kind` | `ItemKind` | 见下 |
| `desc` | string | 描述 |
| `effects` | Effect[] | 见「效果词汇表」 |
| `storyNode` | string | **仅叙事物件用**，指向剧情节点 id |

### 四种 kind

| kind | 行为 |
|---|---|
| `narrative` | **拾起即触发全屏剧情**。必须提供 `storyNode` |
| `consumable` | 玩家主动使用，结算 `effects` 后消耗掉 |
| `relic` | **获得时立刻结算 `effects`**（被动常驻） |
| `key` | 开门用 |

> ⚠️ **叙事物件的 `storyNode` 指向的节点，不要写 `requires`**。
> 物品触发时不该再检查出现条件，否则会出现
> 「东西拿到了，剧情却不弹」这种最让人困惑的 bug。

---

## 五、剧情 `StoryNode`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一 id |
| `text` | string | 正文，用 `\n` 分段。**建议 60~180 字** |
| `quote` | string | 引用块（"书上写着……"那种效果） |
| `requires` | Condition[] | **出现条件**。不满足则不会被填进槽位 |
| `weight` | number | 同槽位多候选时的选取权重 |
| `slots` | SlotType[] | 只在这些槽位类型出现 |
| `minDepth` / `maxDepth` | number | 限定层数区间 |
| `choices` | StoryChoice[] | **至少 1 个**，否则玩家会卡住 |

### 槽位类型

| 类型 | 位置 | 适合放什么 |
|---|---|---|
| `ENTRY` | 入口房 | 引入、建立氛围 |
| `MID` | 中层房 | 支线、lore |
| `PREBOSS` | 楼梯房 | 高潮、重大抉择 |
| `SECRET` | 最偏远房 | 隐藏内容、奖励 |

**不写 `slots` 的节点可以出现在任何槽位** —— 这是最省事也最常用的写法。

---

## 六、选项 `StoryChoice`

| 字段 | 类型 | 说明 |
|---|---|---|
| `text` | string | 选项文字 |
| `requiresTag` | string | **只有拥有该 tag 的角色能看到** |
| `requires` | Condition[] | 其他出现条件 |
| `once` | boolean | 选过一次就不再显示 |
| `effects` | Effect[] | 选了之后发生什么 |
| `next` | string | 跳到另一个剧情节点 |
| `badge` | string | 角标，如 `'记梦者'` |

### ⚠️ 每个节点至少要有一个**不带 `requiresTag`** 的选项

否则没有对应 tag 的角色会遇到「没有选项可选」，直接卡死在剧情层。
（有测试会强制检查这一条）

---

## 七、效果词汇表 `Effect`

这是内容的**唯一写入口**。所有数值变化都必须走这些 kind。

| kind | 参数 | 说明 |
|---|---|---|
| `setFlag` | `key`, `value` | 写一个 flag（结局判定的基础） |
| `addFlag` | `key`, `delta` | flag 数值累加 |
| `sanity` | `delta` | 理智增减（会被钳制在 0~sanMax） |
| `heal` | `amount` | 回血 |
| `damage` | `amount` | 扣血 |
| `buff` | `stat`, `amount` | **永久**改属性。`stat` ∈ `atk`/`def`/`hpMax`/`sanMax` |
| `giveItem` | `defId` | 给一件物品 |
| `message` | `text`, `tone` | 往日志写一行 |
| `goto` | `nodeId` | 跳到另一个剧情节点 |

### `buff` 是「拿理智换力量」的表达方式

```ts
effects: [
  { kind: 'sanity', delta: -12 },              // 代价
  { kind: 'buff',   stat: 'atk', amount: 3 },  // 收益
  { kind: 'setFlag', key: 'traded_flesh', value: true },
]
```

没有 `buff` 的话，内容作者只能写「扣理智 + 回血」，真正的力量成长无法落在属性上。

## 八、条件词汇表 `Condition`

| kind | 参数 | 说明 |
|---|---|---|
| `flag` | `key`, `value?` | flag 存在 / 等于某值 |
| `noFlag` | `key` | flag 不存在 |
| `deaths` | `op`, `value` | 累计死亡次数 |
| `san` / `hp` | `op`, `value` | 当前理智 / 生命 |
| `tag` | `value` | 角色 tag |
| `hasItem` | `defId` | 持有某物品 |
| `depth` | `op`, `value` | 当前层数 |
| `all` / `any` / `not` | `of` | 逻辑组合 |

`op` ∈ `>=` `>` `<=` `<` `==` `!=`

### 用 `deaths` 做"你已经来过这里了"

```ts
requires: [{ kind: 'deaths', op: '>=', value: 1 }]
```

这是本作最重要的叙事机制 —— **死亡不是重来，是又醒了一次**。
死得越多，某些内容才解锁。

## 九、幕与结局 `ActDef` / `EndingDef`

```ts
{
  id: 'act_1', name: '第一幕', floors: 3,
  floorSize: { w: 21, h: 15 },
  roomsPerFloor: [6, 8],
  enemiesPerFloor: [4, 7],
  endings: [ /* ... */ ],
}
```

### 结局

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `name` | string | |
| `priority` | number | **大的先判定** |
| `requires` | Condition[] | 满足则命中 |
| `text` | string | 结算文案 |
| `victory` | boolean | 官方内容**一律 false** |

### ⚠️ 三条硬规则

1. **必须有一个 `requires: []` 的兜底结局**，`priority` 最低。
   否则玩家会走到"没有结局"。
2. **结局依赖的每个 flag 都必须有人写**。
   没人写的 flag = 这条结局永远是死代码（有测试会检查）。
3. **官方内容不含胜利结局**。好结局留给社区扩展。

## 十、分支设计规范

### ❌ 不要这样：选择直接连到下一个节点

```
选择 A → 节点 1 → 选择 B → 节点 2 → ...
```

内容量会指数爆炸。

### ✅ 要这样：选择只写 flag，结局靠条件集合收敛

```ts
choices: [
  { text: '念出那个名字', requiresTag: 'scholar',
    effects: [{ kind: 'setFlag', key: 'knows_the_name', value: true },
              { kind: 'sanity', delta: -10 }] },
  { text: '烧了它',
    effects: [{ kind: 'setFlag', key: 'burned_it', value: true }] },
  { text: '退出去', effects: [] },   // ← 永远保留一个"什么都不做"的选项
]
```

**规则**：
- 大部分分支在 1~2 个节点内收敛回主线
- 只有每章 1~2 个"重大选择"才用 `next` / `goto` 真分岔
- 结局用 `priority` + `requires` 组合判定，**不是一棵树**

## 十一、社区扩展规则

### 命名空间

社区包的 id 必须带命名空间前缀，防止撞车：

```ts
namespace: 'abyss'
// 包内 id 可以写 'abyss:goblin' 或裸 'goblin'
```

### 覆盖原版内容

查找顺序 = 包加载顺序，**靠前的优先**。
你的包如果 `load_after: ['core']`，就能覆盖原版同名 id。

### 世界观律（不可覆盖）

有些东西是硬约束，mod 不许改：

- **死者不归** —— 没有人能复活
- 官方内容里所有角色都会死

社区可以写「你救下了某个人」「她多活了一幕」「你换了一种死法」，
**但不能写「所有人复活」**。

把扩展方向定义成「**不同的死法**」而不是「活下来」——
这样社区创作**增强**主题，而不是拆台。

## 十二、提交前自查清单

项目的测试套件会自动检查这些，本地跑 `pnpm test` 即可：

- [ ] 所有 `storyNode` 指向的剧情节点真实存在
- [ ] 所有 `drop.pool` 里的物品 id 存在，且 `kind` 一致
- [ ] 所有 `giveItem` / `startItems` 引用的 id 存在
- [ ] 所有 `requiresTag` 都真存在于某个角色的 tags 里
- [ ] 每个剧情节点至少保留 1 个非门控选项
- [ ] 每个剧情节点至少 1 个 `choices`
- [ ] 结局依赖的 flag 都有人写
- [ ] 存在 `requires: []` 的兜底结局
- [ ] 所有 id 全局唯一
- [ ] 正文长度 40~400 字

## 十三、参考：一个完整的叙事物件闭环

```ts
// ① 物品
{ id: 'wax_cylinder', name: '蜡筒', kind: 'narrative',
  storyNode: 'story_cylinder_playback' }

// ② 剧情（注意：不写 requires / slots）
{ id: 'story_cylinder_playback',
  text: '蜡筒转动起来。起初只有杂音，然后是一个人的呼吸声——\n' +
        '你听了很久才反应过来，那是你自己的呼吸。',
  choices: [
    { text: '继续听下去', badge: '记梦者', requiresTag: 'scholar',
      effects: [{ kind: 'setFlag', key: 'knows_the_name', value: true },
                { kind: 'sanity', delta: -12 }] },
    { text: '砸了它',
      effects: [{ kind: 'setFlag', key: 'broke_the_cylinder', value: true },
                { kind: 'buff', stat: 'atk', amount: 2 }] },
    { text: '关掉', effects: [] },
  ] }

// ③ 结局
{ id: 'ending_signed_the_shift', name: '接班的人是你', priority: 30,
  requires: [{ kind: 'all', of: [
    { kind: 'flag', key: 'knows_the_name' },
    { kind: 'flag', key: 'signed_the_handover' },
  ]}],
  text: '天亮了。值班表上多出一行你的名字。', victory: false }
```

**链路**：清空房间 → 槽位触发 → 掉出蜡筒 → 玩家拾取 → 全屏剧情 → 选项 → flag → 影响结局。
