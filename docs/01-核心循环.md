# 01 · 核心循环

> 梦境循环 —— 文字肉鸽。一层层往下走，每次变强都要拿理智去换。

---

## 一、一句话定义

> 你在不断崩塌的梦境里向下走，每次变强都要拿理智去换。

**核心张力**：理智既是"命"，也是"货币"。变强和保命抢的是同一个资源。
单资源双用途是肉鸽设计里最优雅的一种张力（杀戮尖塔的血量就是这个套路）。

---

## 二、三层解耦架构

这是整个项目的地基。三层之间**只能通过定义好的接口说话**。

```
┌─ 元叙事层 Meta ──────────────────────────────┐
│ 跨局持久：flags、死亡次数、已见剧情、结局      │  ← 落盘，死亡不清空
└──────────────────────────────────────────────┘
              ↑ 只在"结算点"读写
┌─ 叙事层 Narrative ───────────────────────────┐
│ 局内：剧情节点、选项、效果                     │  ← 编排好的，不随机
└──────────────────────────────────────────────┘
              ↑ 由"叙事槽位"触发
┌─ 地牢层 Dungeon ─────────────────────────────┐
│ 随机生成、回合制、战斗、掉落                   │  ← 完全不知道剧情的存在
└──────────────────────────────────────────────┘
```

**为什么必须解耦**：传统肉鸽的乐趣在"每局都不一样"，剧情的乐趣在"精心编排的因果"。
这两个东西天然互斥。硬缝的结果是玩家三周目了还没遇到关键剧情。

解耦之后：
- 地牢层只负责**预留槽位**，不知道会填什么内容
- 叙事层只负责**往槽位里填**，不知道地图长什么样
- 两边都能独立替换

## 三、核心循环

### 局内（一层）

```
进入楼层
   ↓
探索随机房间 ──→ 遭遇怪物 ──→ 战斗 ──→ 掉落
   ↓                                      │
清空房间 ←────────────────────────────────┘
   ↓
【叙事槽位触发】→ 掉出叙事物件 → 玩家拾取 → 全屏剧情 → 选项 → flag
   ↓
找到楼梯 → 下一层
```

### 局间

```
走完最后一层 → 结局判定（flag 条件集合）→ 结算
   ↓
死亡 → "又在梦里醒了一次" → 回到本幕开头，flags 全部保留
```

---

## 四、叙事槽位：随机的容器，编排的内容

地牢生成器**不生成完整随机地图**，而是生成**带槽位的随机地图**。

| 槽位类型 | 位置 | 用途 | 数量 |
|---|---|---|---|
| `ENTRY` | 入口房 | 引入、建立氛围 | 每层必 1 |
| `MID` | 中层房 | 支线、lore | 每层 1~2 |
| `PREBOSS` | 楼梯房 | 高潮、重大抉择 | 每层必 1 |
| `SECRET` | 最偏远房 | 奖励、隐藏内容 | 30% 概率 |

**这解决了核心矛盾**：地图是随机的（肉鸽感保住），剧情节点必然出现（叙事保证）。

### 惰性填槽

内容**不在生成楼层时选**，而在**房间被清空的那一刻**才选。

为什么：内容的出现条件里常有 `hasItem` / `san` / `flag` 这类**会随时间变化**的量。
生成时就填的话，条件尚未成立的内容永远填不上 —— 作者写了却没人看得见。

### 触发优先级

1. **房间清空** → 槽位触发（主路径）
2. 如果内容库里有对应的**叙事物件** → 掉在槽位坐标上，玩家自己走过去捡
3. 没有对应物品 → 直接弹剧情（不让内容浪费）

**路径 2 是推荐做法**：读剧情因此变成**主动选择**。
讨厌被打断的肉鸽玩家可以直接走开，剧情党一定会去捡。一个机制同时服务两类人。

## 五、分支设计：flag 收敛，不是选择树

**如果每个选择都真分支，12~18 幕的内容量会指数爆炸，一个人永远做不完。**

规则：

1. 选择只写 **flag**（`Effect.setFlag` / `addFlag`），不写流程
2. 大部分分支在 1~2 个节点内**收敛回主线**
3. 只有每章 1~2 个"重大选择"才真分岔（用 `next` / `goto` 链式跳转）
4. **结局不是树，是一个条件集合** — 按 `priority` 从高到低试，第一个满足的胜出
5. 必须有一个 `requires: []` 的兜底结局，否则玩家会走到"没有结局"

这个做法来自 Telltale / 底特律变人，是唯一能做完的方案。

---

## 六、死亡即叙事（本项目最重要的原创点）

传统肉鸽的**永久死亡**和剧情体验是冲突的：死了重来，剧情就断了。

**解法**：

> **死亡不是"读档"，是"又在梦里醒了一次"。**

- `flags` **全部保留** —— 死得越多，你知道得越多
- 某些剧情选项因为 `deaths >= 1` 而解锁（"你已经来过这里了"）
- 死亡本身成为一条叙事线

**这让肉鸽的重复游玩从叙事障碍变成了叙事资产。**
线性剧情游戏永远做不出"用死亡次数解锁内容"这件事。

### 两种"死"必须分清

| 类型 | 触发 | 结果 |
|---|---|---|
| **游戏性死亡** | 战斗打输 | 回到**本幕开头**，hp/san 回满，flags 保留 |
| **叙事性死亡** | 剧情规定的结局 | 本幕结束，进入下一幕 / 全剧终 |

存档粒度 = **幕**。死在第三幕从第三幕开头重来，不是从游戏开头。
否则玩家在第六小时死掉、损失六小时，重开率会被直接杀死 —— 而重开率是肉鸽的命门。

---

## 七、结局设计：官方只做绝望线

**官方内容里，所有角色都会死。没有好结局。**

好结局 / 救赎线**留给社区扩展去写**。官方只定义"什么是不可能的"。

这不是偷懒，是一个更强的设计：
**官方定义死亡的必然性，社区探索死亡的意义。**

社区可以写"你救下了某个人"、"你让她多活了一幕"、"你换了一种死法"，
但不能写"所有人复活" —— 那是世界观律，在 Schema 层做硬约束。

更好的引导：把社区的扩展方向定义成「**不同的死法**」而不是「活下来」。

## 八、理智：本作的核心资源

理智 `san` 是第二条血条，但它同时是**货币**：

| 用途 | 代价 |
|---|---|
| 读懂不该读的东西（拿情报） | 扣理智 |
| 换取力量（`buff` 加攻击） | 扣理智 |
| 硬扛恐怖场景 | 扣理智 |

**低理智时的被动流失**（san ≤ 30 时每回合 -1）制造了"必须尽快结束"的压力，
让"变强 vs 保命"的取舍真正有代价，而不是可以无限拖延。

**文字在这里是优势而非妥协**：状态不直给数字，而是描述 ——
HP 低就写"你的手在抖"，SAN 低就写"墙上的影子比刚才多了一个"。
这个设计只有文字能做，换成图形界面反而没味道了。

## 九、三个模式

```
        ┌──────────────────────────────────────┐
        │  core   引擎 / 规则 / 数据 Schema      │
        └──────────────────────────────────────┘
              ↑            ↑             ↑
      ┌───────────┐ ┌───────────┐ ┌──────────────┐
      │  主线模式  │ │ 闯关模式   │ │  扩展模式     │
      │ 地牢+叙事  │ │ 纯地牢     │ │ 加载社区 pack │
      │ 慢/重体验  │ │ 快/重 build│ │ 任意          │
      └───────────┘ └───────────┘ └──────────────┘
```

三个模式**共享同一个 core**，差别只在"装了什么内容 + 启不启用叙事引擎"。

- **主线** = 地牢生成 + 叙事引擎 + 元叙事落盘
- **闯关** = 地牢生成 + 波次编排，**叙事引擎不加载**（所以天然更快更纯粹）
- **扩展** = 加载社区 pack，三个模式都能被 mod 扩展

## 十、工程纪律（不可违反）

1. **`core` 里禁止出现 `window` / `document` / DOM / CSS**
   所有表现相关的东西通过 `GameEvent` 往外交。
   破坏了这条，core 就无法在 node 里跑测试，也没法复用到 TUI / 桌面壳 / 服务端。

2. **禁止 `Math.random()`**
   随机性只能来自 `state.rngState`。同一个 seed 必须复现同一局 ——
   否则 bug 无法定位，玩家也无法分享"神种"。

3. **`reduce(state, intent)` 是纯函数**
   同样的输入必然得到同样的输出，不读全局变量。

4. **所有输入源只产出 `Intent`**
   虚拟方向键 / 点格子 / 滑动 / 键盘 / 手柄 → `Intent` → core。
   core 收到 Intent 时**不知道**玩家用的是手机还是键盘。

5. **内容里禁止出现代码，代码里禁止出现具体内容**
   加 100 个怪不改一行引擎代码。

这五条带来的实际收益：
- 单元测试直接喂 Intent 序列，不用模拟触摸事件
- 存档 = 序列化 state，没有隐藏状态
- 回放/录像 = 录 Intent 流（肉鸽社区很吃这个）
- 打包成 exe / apk 时，游戏逻辑零改动

## 十一、MVP 边界

**第一幕 demo 的范围**：

| 项 | 内容 |
|---|---|
| 角色 | 2 个（必须 2 个，否则验证不了 tag 门控） |
| 幕结构 | 1 幕 = 3 层，每层 6~8 房间，21×15 格 |
| 叙事节点 | 10 个 |
| 怪物 | 6 种 |
| 物品 | 10 件（3 叙事物件 / 3 消耗品 / 3 遗物 / 1 钥匙） |
| 结局 | 3 个（全部是死亡结局） |
| 目标时长 | 30~45 分钟 |

**不做**：闯关模式、扩展模式、社区 pack 加载、移动端打包、联机。
